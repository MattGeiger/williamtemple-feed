# Roadmap: v1.6.0 → v1.9.5

Planning document, drafted 2026-08-19 with 1.5.0-beta.21 in production. Nothing
here is committed work. Versions are a running order, not a schedule — each one
should ship when it is worth deploying, the way 1.5.0 did.

Two rules carried forward from 1.5.0, because both were learned expensively:

- **A version number marks "ran in production and staff accepted it"**, not "the
  code is written". Five versions were cut between beta.16 and beta.20 and none
  of them reached the Pi; the fixes inside them sat unexercised for five days
  and two defects surfaced within an hour of finally deploying.
- **Deploy smaller, more often.** The beta.16 → beta.21 jump was manageable only
  because the schema happened not to change. It was not a plan.

## v1.6.0 — Purchase Log

### Sidebar restructure

Rename the **Service** section to **Logs**, holding:

- Service Log (existing)
- Purchase Log (new)

The rename earns its place: the section is about hand-kept daily records, and a
second one makes "Service" actively misleading. Check `navigation.ts` and the
user guides for the old label — several guides name the section directly.

### The feature

An `EnhancedDataTable` of spending **outside OFB** — the Costco run for cases of
eggs, the cash-and-carry trip when a delivery falls short. Multi-step modal to
add an entry:

| Field | Source |
|---|---|
| Purchase name | free text ("Eggs") |
| Category | `Category` table, the same list Inventory uses |
| Quantity | number (18) |
| Unit | dozen, case, lb, each |
| Price | money, stored in cents |
| Date | purchase date |

Bulk and single-row actions (edit, delete), per the table standard.

### The architectural question to settle first

**Procurement is currently 100% import-derived.** Every row traces to an OFB
export through `ProcurementImport` → `ProcurementOrderRevision`, and
`PROCUREMENT_CHANNELS` has three members, all of them import-shaped:

```ts
export const PROCUREMENT_CHANNELS = ['ofb_warehouse', 'fresh_alliance', 'community_donation'] as const;
```

A Purchase Log is **hand-entered**, like the Service Log. So the decision is
whether local purchases become a fourth channel inside the procurement model, or
a parallel record that Procurement Analytics reads alongside it.

Leaning: **a fourth channel, `local_purchase`, with an explicit
`ProcurementEventKind` of its own.** It really is procurement — food arriving by
a different route — and forcing it outside the model would mean every spend
card learning to add two sources together. But it must carry its provenance:
a hand-entered figure and an OFB invoice line are not the same kind of fact, and
`AGENTS.md` already requires a card to say which record produced its figure.

Note the precedent for a conditional channel: `community_donation` is filtered
out of `channelMix` until it holds weight, because a permanently-zero row would
imply every agency has a source it will never have. `local_purchase` should
behave the same way for agencies that never buy locally.

**Not** an instance of "never sum the two records" — that rule exists because
intake and the Service Log are two measures of *the same* pantry days. Local
purchases and OFB deliveries are disjoint events; adding them is correct.

### Analytics that fall out of it

- OFB Spending Over Time gains a second series, or a companion card.
- Total food cost becomes answerable for the first time — currently the pantry
  can only see what OFB charged.
- Cost per household, if it is wanted, needs care: it divides a partial cost by
  a complete household count unless *all* spend is captured.

### Watch for

- **Money is cents, integer.** The procurement service is consistent about this
  (`productChargesCents`, `netRecordedCostCents`); a float here would be a
  rounding bug that shows up in a funder report.
- **Units are not weights.** "18 dozen" cannot join the weight charts without a
  conversion nobody has defined. Keep purchases out of weight series until
  someone decides what a dozen eggs weighs — or never.
- Revision semantics: does editing a purchase supersede or mutate? The rest of
  the domain supersedes. Follow it, or state why not.

## v1.7.0 — Shopping List grid layouts

Planned but never built. Adds 2×2 / 2×3 grid layouts alongside the existing
split layout, so a list can hold a small built form — checkboxes, text lines,
written-response fields — with per-segment translation settings exactly as
split layout has them.

This is capability work: the goal is that Shopping Lists stop being one shape
and start supporting the range of contexts staff actually print for.

Sequencing note: **do this before v1.8.0.** Redesigning the interaction model
(1.8.0) around a layout set that is about to change would be wasted work, and
grid layouts will themselves reveal where the current controls strain.

## v1.9.0 — LOTTO integration

LOTTO logs every queue-management action as an atomic event, which answers
questions Operations analytics currently cannot:

- tickets issued on a given date
- tickets unclaimed or returned
- typical wait time in the queue (derived)

### What it needs

- **Stored API credentials for a Neon-hosted Postgres.** FEED already encrypts
  LLM API keys — `KeyManager.getActiveKey`, with the active key in the
  `EncryptionKey` table rather than an env var. Reuse that; do not invent a
  second secret store.
- **A Postgres client.** A genuinely new dependency and a second database
  dialect in a project that has only ever spoken SQLite. That is the real cost,
  not the integration logic.
- **Parallel work in LOTTO**, likely — a read-only role and a stable query
  surface at minimum.

### Decide early: pull or push, and what is stored

Does FEED query LOTTO live for each analytics request, or ingest events on a
schedule into local tables? Live queries make the Pi's analytics depend on
Neon's availability and on the tunnel; ingestion makes them fast and offline-safe
but adds a sync path to get wrong. Given the Pi's constraints and that analytics
here is historical rather than real-time, **ingestion looks right**.

**PII boundary applies unchanged.** Whatever LOTTO holds about individuals, FEED
should ingest counts and timings, not identities. Wait time is derived from
timestamps; it does not need to know whose ticket it was.

## v1.9.5 — LLM catalogue and pricing audit

**Two corrections to the premise, both checked in the code today.**

**1. The catalogue is already current.** `model-specs.ts` already carries every
model on the list, plus reasoning models and older Claudes:

```
gpt-5-nano, gpt-5-mini, gpt-5, gpt-4.1-nano, gpt-4.1-mini, gpt-4.1,
gpt-4o-mini, gpt-4o, o4-mini, o3-mini, o3,
claude-3-5-haiku, claude-haiku-4-5, claude-sonnet-4-5, claude-sonnet-4,
claude-3-7-sonnet, claude-opus-4-5, claude-opus-4,
gemini-2.5-flash-lite, gemini-2.5-flash, gemini-2.5-pro,
gemini-3-flash-preview, gemini-3-pro-preview
```

So "add support for newer models" is largely done. What remains is genuinely
your second point:

**2. The pricing audit is real and cannot be done from inside the repo.**
Published prices move, and stored prices drive cost projections and the daily
and monthly spend limits. A stale figure does not error — it silently
mis-projects, which is the same class of failure as the household count. This
needs checking against each provider's current price page, with the date of the
check recorded in the file.

**3. A latent bug found while checking: the catalogue is duplicated.**

- `packages/backend/src/services/ai/model-specs.ts`
- `packages/frontend/src/components/ai-configuration/model-specs.ts`

The two model lists are **identical today**, and nothing enforces that. Update
one and the interface offers a model the backend cannot price, or prices it
differently from what it charges against a limit. Either extract a shared module
or add a drift-guard test — the same pattern that already protects analytics
card coverage and, since beta.21, the import status union.

Also consider: retire preview model ids once they go GA, and decide whether the
catalogue should carry a deprecation flag rather than silently keeping models
that providers have withdrawn.

## Unversioned — candidates worth placing

Not assigned to a release. Several are cheap and reduce risk more than a feature
would.

### Rehearse a restore

**#73** (restore aborted on any instance with AI usage telemetry) is deployed but
has never been exercised against real data. Restore is the recovery path — its
failures appear for the first time during an actual recovery, which is the worst
possible moment. A scheduled drill onto a scratch database, from the real
production backup, would convert a hope into a fact. Cheap, and it is the single
highest-value item in this section.

### Surface import quality warnings

The SIMC re-import reported *"FEED retained 24 structured quality warnings"* and
*"24 visits have a member-row difference"*. That analysis is genuinely useful to
staff correcting their data at source — and as far as the deploy showed, it is
visible only at import time. Worth checking whether those warnings are reachable
afterwards; if not, they are data being collected and discarded.

### The 2017–2020 service gap

FEED's Link2Feed visits begin 2020-10-19; the pantry's records reach back to
2017. **The client export cannot close this** — it carries no dates, which is
why that import path was closed (see the memory note and
`source-contracts.ts`). A *visits* export for 2017–2020 would close it, and is a
different file that may or may not be obtainable. Worth one question to SIMC or
Link2Feed before assuming it isn't.

### Link2Feed as frozen legacy

SIMC is the live system; Link2Feed is closed history that can no longer be
checked against its own UI. At some point the L2F adapter should be explicitly
frozen — documented as legacy, its data treated as immutable, and no new feature
built on assumptions about its semantics. The eligibility misreading and the
closed client-export question were both symptoms of treating a dead source as
interrogable.

### Standing debt

- **TypeScript**: ratchet baseline is **227** (`typecheck-baseline.json`,
  2026-08-16); `docs/TSC-DEBT.md` still says **230**. Doc drift — fix the doc.
  The systemic `EnhancedDataTable` / `TableRowAction` generics fix remains the
  real reduction and needs its own scoped pass.
- **Lint**: 507 problems (332 errors) is the accepted baseline. It should be a
  ratchet like the type check, or it will only ever grow.
- **Accessibility**: the release triage notes ~12 missing `DialogTitle`
  warnings on `/food-items` alone (#27b). Quick with `<VisuallyHidden>`.
- **Security review** (#7): AGPL and a public repo mean external eyes on the
  auth path. Still outstanding.

### Operational

- The Pi's card sat at **82% full** before this deploy; clearing obsolete images
  recovered 6 GB. That is a recurring chore, not a fix — worth a documented
  prune step in the deploy runbook, or a scheduled one.
- `production.db` is **254 MB** and grows with every import. No retention or
  archive policy exists. Not urgent; worth deciding before it is.
