# Roadmap: v1.6.0 → v2.0

Planning document, drafted 2026-08-19 with 1.5.0-beta.21 in production. Nothing
here is committed work. Versions are a running order, not a schedule — each one
should ship when it is worth deploying, the way 1.5.0 did.

## Gate on 1.5.0 final — rehearse a restore

**1.5.0 does not get its final version number until a restore has been proven
against real data.** #73 (restore aborted on any instance with AI usage
telemetry) is deployed but has never run against anything real, and restore is
the recovery path — its failures otherwise debut during an actual recovery.

The drill, which risks nothing in production:

1. Download the production backup to the Mac.
2. Restore it onto a **scratch copy** of the localhost dev database, not the dev
   database itself.
3. **Precondition: the target must already hold AI usage telemetry.** #73 was
   specifically a foreign key from usage records into the AI configuration being
   replaced. Restore onto a clean database and the drill passes without ever
   touching the bug.
4. Verify the same figures the deploy verified: 82,613 encounters at the
   pre-import mark, and `Hispanic, Latino, or Spanish` whole rather than in
   three fragments.

Local logs, local tests, and a fast loop if anything breaks — none of it near
the Pi.

---

Two rules carried forward from 1.5.0, because both were learned expensively:

- **A version number marks "ran in production and staff accepted it"**, not "the
  code is written". Five versions were cut between beta.16 and beta.20 and none
  of them reached the Pi; the fixes inside them sat unexercised for five days
  and two defects surfaced within an hour of finally deploying.
- **Deploy smaller, more often.** The beta.16 → beta.21 jump was manageable only
  because the schema happened not to change. It was not a plan. The narrow
  lesson is not "beta code had bugs" — it did, and that is what beta is for,
  and nothing that already worked regressed. It is that five versions sat
  undeployed for five days and nobody knew whether any of it worked. Keep a
  verified stable build in production and deploy beta builds only when there is
  a reason to.

## v1.6.0 — Purchase Log

### Sidebar restructure

Rename the **Service** section to **Logs**, holding:

- Service Log (existing)
- Purchase Log (new)

The rename earns its place: the section is about hand-kept daily records, and a
second one makes "Service" actively misleading. Check `navigation.ts` and the
user guides for the old label — several guides name the section directly.

### The feature

An `EnhancedDataTable` of spending **outside OFB** — the Costco run for cases of
eggs, the cash-and-carry trip when a delivery falls short. Multi-step modal to
add an entry:

| Field | Source |
|---|---|
| Purchase name | free text ("Eggs") |
| Category | `Category` table, the same list Inventory uses |
| Quantity | number (18) |
| Unit | dozen, case, lb, each |
| Price | money, stored in cents |
| Date | purchase date |

Bulk and single-row actions (edit, delete), per the table standard.

### The architectural question to settle first

**Procurement is currently 100% import-derived.** Every row traces to an OFB
export through `ProcurementImport` → `ProcurementOrderRevision`, and
`PROCUREMENT_CHANNELS` has three members, all of them import-shaped:

```ts
export const PROCUREMENT_CHANNELS = ['ofb_warehouse', 'fresh_alliance', 'community_donation'] as const;
```

A Purchase Log is **hand-entered**, like the Service Log. So the decision is
whether local purchases become a fourth channel inside the procurement model, or
a parallel record that Procurement Analytics reads alongside it.

Leaning: **a fourth channel, `local_purchase`, with an explicit
`ProcurementEventKind` of its own.** It really is procurement — food arriving by
a different route — and forcing it outside the model would mean every spend
card learning to add two sources together. But it must carry its provenance:
a hand-entered figure and an OFB invoice line are not the same kind of fact, and
`AGENTS.md` already requires a card to say which record produced its figure.

Note the precedent for a conditional channel: `community_donation` is filtered
out of `channelMix` until it holds weight, because a permanently-zero row would
imply every agency has a source it will never have. `local_purchase` should
behave the same way for agencies that never buy locally.

**Not** an instance of "never sum the two records" — that rule exists because
intake and the Service Log are two measures of *the same* pantry days. Local
purchases and OFB deliveries are disjoint events; adding them is correct.

### Analytics that fall out of it

- OFB Spending Over Time gains a second series, or a companion card.
- Total food cost becomes answerable for the first time — currently the pantry
  can only see what OFB charged.
- Cost per household, if it is wanted, needs care: it divides a partial cost by
  a complete household count unless *all* spend is captured.

### Watch for

- **Money is cents, integer.** The procurement service is consistent about this
  (`productChargesCents`, `netRecordedCostCents`); a float here would be a
  rounding bug that shows up in a funder report.
- **Units are not weights.** "18 dozen" cannot join the weight charts without a
  conversion nobody has defined. Keep purchases out of weight series until
  someone decides what a dozen eggs weighs — or never.
- Revision semantics: does editing a purchase supersede or mutate? The rest of
  the domain supersedes. Follow it, or state why not.

## v1.7.0 — Shopping List grid layouts

Planned but never built. Adds **2×2, 2×3, and 2×4** grid layouts alongside the
existing split layout, so a list can hold a small built form — checkboxes, text
lines, written-response fields — with per-segment translation settings exactly
as split layout has them. All three sizes are part of the active Builder
contract: four larger segments, six medium segments, or eight compact segments
per Letter page. Older print-system documents mention only 2×3 / 2×4; they are
legacy implementation notes, not a reason to omit 2×2 from the new Builder.

This is capability work: the goal is that Shopping Lists stop being one shape
and start supporting the range of contexts staff actually print for.

Sequencing note: **do this before v1.8.0.** Redesigning the interaction model
(1.8.0) around a layout set that is about to change would be wasted work, and
grid layouts will themselves reveal where the current controls strain.

## v1.8.0 — Shopping List UX

The current builder is a working v1.0 MVP. Control layout is clunky in parts and
the hierarchy is questionable — it does the job without being good at it.

Deliberately scoped as a rework of *interaction*, not of *capability*: v1.7.0
adds what lists can do, v1.8.0 makes doing it pleasant. Keep the staff workflow
recognisable; this is the tool people use under time pressure on a service day.

The brief is layout, nesting, and hierarchy, measured against known issues and
against how comparable tools solve the same interaction problems. That is a
design judgement call and it belongs to the designer — it does not need to be
reduced to acceptance criteria before it can start. Iterative design with AI
tooling makes this clay rather than stone: shape it, look at it, reshape it.

Related open item: **#49** — Document Translator cleanup toward the same
standard, without changing its staff workflow. Worth folding in if the two share
components.

## v1.9.0 — LOTTO integration

LOTTO (`~/Repos/lotto`, v1.20.1, Next.js 16 on Vercel + Neon Postgres) manages
the ticketed queue. Its data answers questions Operations analytics currently
cannot:

- tickets issued on a given date
- tickets unclaimed or returned
- queue pace from the time between calls (derived)

The two apps already have a contract, in the other direction: LOTTO's
`/inventory` page reads FEED's public inventory endpoint. This is the mirror
image.

### PREREQUISITE — a durable daily record in LOTTO, and it is urgent

**LOTTO does not currently keep an event log, and its history expires.** Checked
in the source on 2026-08-19:

- `raffle_state` is a **singleton row** (`where id = 'singleton'`), overwritten
  as the day proceeds.
- History exists only as `raffle_snapshots`, which are undo-points, and they are
  pruned: `cleanupOldSnapshots(retentionDays = 30)`.

So LOTTO can answer "what happened in the last 30 days, if a snapshot happens to
sit at the right moment." It cannot answer "how many tickets were issued in
March." Whatever FEED builds inherits that ceiling.

**The fix belongs in LOTTO's next release, not alongside FEED v1.9.0.** On
**Reset for New Day**, close the active raffle session into an append-only daily
summary before clearing it: ticket range, issued, generated, called, unclaimed,
returned, and a privacy-minimized call timeline. The closeout needs a stable
session id so a retried reset is idempotent and an undo followed by another
reset can append a revision instead of duplicating or mutating history.

The source review corrected one earlier assumption: `calledAt` holds the latest
call timestamp for each ticket, not an issuance timestamp or a complete event
log. It supports **queue pace** (for example, median time between distinct
ticket calls), not actual client wait time. Calling that value “wait time” would
invent a fact LOTTO does not observe. Actual wait time remains out of scope
unless LOTTO later records when each ticket is issued.

**Why the urgency:** every service day that passes without a durable record is
permanently lost after 30 days. Add the daily record soon and FEED v1.9.0 opens
against a year of history. Defer it and v1.9.0 ships against 30 days.

### Integration shape: an endpoint, not a database connection

An earlier draft of this plan proposed that FEED hold credentials to LOTTO's
Neon Postgres and query it directly. **That was wrong.** It would put a foreign
database's credentials in FEED, add a second SQL dialect to a project that has
only ever spoken SQLite, and couple FEED to LOTTO's schema so that a LOTTO
migration could break FEED's analytics.

Instead: **LOTTO exposes a versioned, read-only daily-summary endpoint; FEED
ingests it on a schedule.** LOTTO already serves `/api/*` routes, so this is a
known shape in a codebase we own. Symmetric with the integration that already
exists, no schema coupling, no foreign database credentials, and it tolerates a
flaky tunnel because ingested data is local by the time a chart reads it.

Ingest rather than query live: the Pi should not have its analytics depend on
Neon's availability, and these are historical questions, not real-time ones.

The endpoint **must** use machine-to-machine bearer authentication rather than a
staff browser session. LOTTO owns an integration token in deployment
configuration; FEED's existing encrypted key storage (`KeyManager.getActiveKey`,
active key in the `EncryptionKey` table rather than an env var) is the right
home for FEED's copy. Do not invent a second FEED secret store.

**PII boundary applies unchanged.** FEED ingests counts and timings, not
identities. Queue pace is derived from a timestamp-only timeline; it never
needs to know whose ticket it was or even the ticket number.

The reviewed v1 contract, revision semantics, endpoint envelope, and acceptance
criteria are in
[`lotto-daily-summary-contract.md`](lotto-daily-summary-contract.md). A
self-contained implementation prompt for an AI agent working in the LOTTO repo
is in
[`lotto-daily-summary-agent-prompt.md`](lotto-daily-summary-agent-prompt.md).

So "add support for newer models" is largely done. What remains is genuinely
your second point:

**2. The pricing audit is real and cannot be done from inside the repo.**
Published prices move, and stored prices drive cost projections and the daily
and monthly spend limits. A stale figure does not error — it silently
mis-projects, which is the same class of failure as the household count. This
needs checking against each provider's current price page, with the date of the

- `packages/backend/src/services/ai/model-specs.ts`

catalogue should carry a deprecation flag rather than silently keeping models
that providers have withdrawn.

## v2.0 — Prisma 7, and FEED off the rack

Two separate pieces of work that must not ship together.

### Split them

**Prisma 6 → 7 is a major version on the layer every query passes through.** It
has no user-visible payoff, which is exactly why it should go first and go
quietly. Bundling it with a broad surface change means that when something
breaks, there are two candidate causes and no way to tell them apart. (Latest
stable is the 7.x line; 6.19.x is only the latest 6.)

### ONE DEPLOYMENT PER AGENCY. NOT MULTI-TENANCY.

**This is a hard constraint and it is easy to erode by accident.**

White-label means each agency runs **its own instance**, with its own branding,
its own configuration, and **its own database**. It does **not** mean one
database holding several agencies' rows behind an agency filter.

The two look nearly identical in a planning document and are opposites in the
schema. `AGENTS.md` opens with the shared-whole-organization principle and marks
it hard-won: shopping-list templates originally shipped with an `ownerId`
partition that sequestered each user's data behind their own login, and it had
to be torn out (#31). A `tenantId` column would be that same mistake at a larger
scale, and someone will propose one in good faith unless this says otherwise in
plain terms.

The model is Blender, not Salesforce: a free tool an agency downloads,
configures, and runs. Not a hosted service on one domain. Every user inside a
deployment continues to share one dataset — that is the point, not a limitation.

### The port is de-risked — LOTTO already did it

LOTTO ships typed, deployment-selected brand profiles with database-backed
appearance configuration, live since 2026-07-17 and proven by a second agency
deployment. See `~/Repos/lotto/docs/WHITE_LABEL_BRANDING_PLAN.md` and
`CONFIGURABLE_BRANDING_PLAN.md`.

Code has already flowed FEED → LOTTO once (the AI configuration and translation
system). This is the return trip, between two codebases under the same
ownership. That makes v2.0's headline feature a port of a working pattern rather
than a design from scratch.

### Localization scope — much narrower than it first appears

**FEED's interface is English-only, and there is no UI i18n framework at all** —
no `react-i18next`, no `next-intl`, no locales directory. Verified 2026-08-19.
The multilingual surface is **output**: the document translator, generated
shopping lists, and the public inventory endpoint, backed by content tables
(`CategoryTranslation`, `FoodItemTranslation`, `Language`, `Translation`).

LOTTO is the one that needs sophisticated configurable semantics, because LOTTO
is client-facing with a multilingual UI. Do not import that constraint here. A
FEED rename does **not** multiply across eight languages.

The real surface is **85 occurrences in non-test source** (license headers
excluded — every file's SPDX block names William Temple House branding, which is
a trademark notice, not a string to configure), plus docs, user guides, in-app
help, and PDF templates. Single language. Sizeable but ordinary.

### Two different problems wearing the same coat

**Brand configuration** — name, logo, colours, metadata, install identity. Port
LOTTO's pattern. Mechanical.

**Deployment capability configuration** — which import sources exist, which
known-event rules apply, which metric defaults ship. This is the real design
work, and its precedent is not branding: it is the administrator-configurable
Service Metric definitions FEED already has.

Names like `wth_tracking` are **deliberately** agency-specific so that a
white-label deployment does not silently inherit them. That information
architecture now lives more durably in the Service Log interface; the WTH
Tracking import is a one-off for one agency's spreadsheet history.

**But do not discard the pattern with the instance.** The hardcoded
historical-event recognition — the 264-person Thanksgiving clicker count — is
worth generalising, because *every* agency will have quirks in real data. A
prompt that says

> "Did you have a large event that explains this household of 324 people?"

is enormously better than a generic validator announcing a value three standard
deviations from the mean. FEED was built against real operational data rather
than a synthetic happy path where every row is well shaped, and that is a
genuine advantage to carry into a product other agencies adopt. The
generalisation is *configurable quirk rules with plain-language explanations* —
the specific rule is WTH's; the idea is everyone's.

## Unversioned — candidates worth placing

Not assigned to a release. Several are cheap and reduce risk more than a feature
would.

### Surface import quality warnings

The SIMC re-import reported *"FEED retained 24 structured quality warnings"* and
*"24 visits have a member-row difference"*. That analysis is genuinely useful to
staff correcting their data at source — and as far as the deploy showed, it is
visible only at import time. Worth checking whether those warnings are reachable
afterwards; if not, they are data being collected and discarded.

### The 2017–2020 service gap

FEED's Link2Feed visits begin 2020-10-19; the pantry's records reach back to
2017. **The client export cannot close this** — it carries no dates, which is
why that import path was closed (see the memory note and
`source-contracts.ts`). A *visits* export for 2017–2020 would close it, and is a
different file that may or may not be obtainable. Worth one question to SIMC or
Link2Feed before assuming it isn't.

### Link2Feed as frozen legacy

SIMC is the live system; Link2Feed is closed history that can no longer be
checked against its own UI. At some point the L2F adapter should be explicitly
frozen — documented as legacy, its data treated as immutable, and no new feature
built on assumptions about its semantics. The eligibility misreading and the
closed client-export question were both symptoms of treating a dead source as
interrogable.

### Standing debt

- **TypeScript**: ratchet baseline is **227** (`typecheck-baseline.json`,
  2026-08-16); `docs/TSC-DEBT.md` still says **230**. Doc drift — fix the doc.
  The systemic `EnhancedDataTable` / `TableRowAction` generics fix remains the
  real reduction and needs its own scoped pass.
- **Lint**: 507 problems (332 errors) is the accepted baseline. It should be a
  ratchet like the type check, or it will only ever grow.
- **Accessibility**: the release triage notes ~12 missing `DialogTitle`
  warnings on `/food-items` alone (#27b). Quick with `<VisuallyHidden>`.
- **Security review** (#7): AGPL and a public repo mean external eyes on the
  auth path. Still outstanding.

### Operational

- The Pi's card sat at **82% full** before this deploy; clearing obsolete images
  recovered 6 GB. That is a recurring chore, not a fix — worth a documented
  prune step in the deploy runbook, or a scheduled one.
- `production.db` is **254 MB** and grows with every import. No retention or
  archive policy exists. Not urgent; worth deciding before it is.
